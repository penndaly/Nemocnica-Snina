Executive summary

Nemocnica Snina is a community hospital in Eastern Slovakia (Prešov region). This platform replaces a static website with a fully operational bilingual digital service: a public-facing hospital site, a patient-facing portal with telemedicine and wearable device integration, and a production CMS that non-technical hospital staff can operate without IT involvement.

The platform is feature-complete in mock mode. The core scaffold (117 files across Phases 0–9 of the build guide) is committed. Telemedicine sprints S6–S11 are complete. Admin backend sprints A1–A3 are complete and merged to main. Wearables W1 + W4–W6 are on main. Sprints W2, W3, and WL9 are all committed on feature/wearables-wl9 — ready to merge. The path to go-live is the L1–L9 launch gate — external credential injection, pen-test, content sign-off, and a controlled soft-launch (FRO pilot clinic first).

Soft-launch target: FRO pilot clinic

The FRO (Fyziatricko-rehabilitačné oddelenie / Physiatry & Rehabilitation) is the designated pilot clinic for online booking. All other clinics are read-only at launch. After a clean burn-in period (1–2 weeks), booking opens for all bookable=true clinics respecting their individual rules.

08

Architecture decisions log

All decisions below are locked. Do not re-open without strong justification — each has downstream consequences.

CMSKeep Strapi i18n plugin — not JSON {sk,en} per-field

A1 originally specified JSON bilingual fields. The shipped Strapi on main uses the native i18n plugin. With Ukrainian + Polish on the roadmap (6 locales total), i18n wins decisively — adding a locale is a Strapi config change, not a field migration. JSON {sk,en} would require migrating every field to {sk,en,pl,uk,cs,hu} and rewriting every API response.

AuthBrowser → Next proxy → NestJS (httpOnly cookie — JWT never in browser)

All portal API calls route through a Next.js proxy layer. The patient JWT is held in an httpOnly secure cookie and is never accessible to client-side JavaScript. This is the repo's established security pattern; wearables and telehealth both follow it.

AuthStaff JWT is separate from patient JWT

Different signing key (STAFF_JWT_SECRET), different aud claim (ns.staff). Staff tokens are never accepted on patient endpoints and vice versa.

Data modelNo physicians table — physician–patient via TelehealthSession

CLAUDE.md forbids a physicians table. Physician–patient relationships are resolved via TelehealthSession. Critical-alert SMS routes to a configurable escalation number (WEARABLES_ALERT_SMS_TO) until per-physician routing is available via A2 staff accounts.

HISNo direct web → HIS DB writes — all via RabbitMQ → sync agent → HL7/FHIR

Every HIS event is published to RabbitMQ and consumed by the sync agent, which translates to HL7 FHIR R4 (HL7 v2 fallback). The web tier never writes directly to the HIS database. Dead-letter queues capture failures for reconciliation.

FHIRReadings with fhir_observation_id are never deleted

Once a wearable reading has been exported as a FHIR Observation to HIS, it cannot be deleted — not even on consent withdrawal. The reading row is preserved; the patient_token reference is anonymised on GDPR erasure. Consent withdrawal soft-deletes readings without fhir_observation_id only.

WearablesOAuth state: consumeState is the single consume point

Renamed from validateState. The service performs a one-time Redis DEL on use (WL9). Adapters receive state read-only — Dexcom and Google re-derive PKCE statelessly, so no double-consume hazard. Fail-closed: any Redis error returns 503 rather than allowing replay.

WearablesRegistry circular-DI: OnModuleInit.register() over constructor injection

ConsumerAdaptersModule self-registers into the W2 AdapterRegistry via OnModuleInit.register(). Constructor injection would create a Medical ↔ Consumer circular dependency. This pattern is the canonical NestJS solution and is safe for the registry's read-after-init use case.

WearablesGarmin OAuth-1.0a async handshake deferred

The synchronous getAuthUrl interface cannot accommodate Garmin's async request-token pre-step. getAuthUrl throws explicitly rather than returning fake success. Push semantics are real: syncReadings → [], webhook handler not duplicated, deregister revokes on the Garmin side. Full OAuth-1.0a support is a separate tracked task.

WearablesLIBRE_REGION: z.enum(['eu']).default('eu') — not "reject absence"

The spec said no default and reject absence in production. Shipping with a default of 'eu' (non-EU still rejected) avoids breaking the existing prod-config test suite and every unset environment. Security outcome is identical — non-EU is always rejected. Deviation documented here and in the branch.

QA/QCWithings measure-type mapping corrected (clinical correctness)

The original W2 mapping had meastype 11=SpO2 and 88=heart rate. Per the Withings API, 11=heart pulse, 54=SpO2, 88=bone mass. A resting pulse of 72 would have been stored as “SpO2 72%” and triggered a critical alert; real SpO2 was never ingested. Fixed in QA/QC commit 921a5e5 along with the getmeas request filter and weight heuristic (value×10^unit exponent replaces the >1000÷1000 gram guess).

QA/QCBatch-alert digest: atomic Lua drain over LRANGE+DEL+SREM

The original WL9 digest cron ran LRANGE, DEL, and SREM as separate commands. On multi-instance deployments two cron instances could both read the same window and each send a digest SMS. Replaced with a single atomic Lua script that drains the list in one Redis round-trip; only the winner gets a non-empty result. TTL is now anchored to window-close, not first-append, so a late cron tick can’t expire data before flush.

QA/QCDexcom initial sync: lastSyncAt=null on device creation

Devices were created with lastSyncAt=now, which tripped Dexcom’s own 5-min rate-limit guard on the connect-time pull — returning an empty reading set with no error. Fixed to lastSyncAt=null so the initial sync correctly requests from the beginning of the available window.

QA/QC3 new migrations added by security remediation

staff_totp_single_use — TOTP anti-replay table (prevents token reuse within the 30-second window). payment_receipt_owner — adds owner column to receipts; download + list routes now filter by owner. his_sync_log — FHIR export idempotency dedup table (claim/release pattern). All three must run before the coordinated web+api deploy. JWT audience checks will reject pre-existing tokens lacking the new aud claim — cleared within 30 min (patient) / 8 h (staff) of deploy.

LaunchSoft-launch: FRO pilot clinic only first

Online booking is enabled for FRO (Fyziatricko-rehabilitačné oddelenie) only at soft-launch. All other clinics are read-only. Full launch follows after a clean 1–2 week burn-in. A documented rollback (per-clinic kill switch + full traffic rollback) is mandatory.

PaymentsGP webpay primary, Stripe-EU backup — no PAN ever touches our servers

Payments use hosted fields / redirect. LSPP emergency fee €1.99. Webhook signature-verified. Payment receipts (PDF) generated server-side via Gotenberg/Puppeteer (EU only).

Language roadmap

The platform is built for six languages. Slovak is the human-authored source of truth. English is human-authored alongside it. Four additional locales are machine-translated with a mandatory human review gate before publish.

With Ukrainian and Polish confirmed on the roadmap, the Strapi i18n plugin (not JSON per-field bilingual) is the correct architecture — adding a locale is a Strapi config change, not a DB migration.
