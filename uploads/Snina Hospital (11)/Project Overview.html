01

Executive summary

Nemocnica Snina is a community hospital in Eastern Slovakia (Prešov region). This platform replaces a static website with a fully operational bilingual digital service: a public-facing hospital site, a patient-facing portal with telemedicine and wearable device integration, and a production CMS that non-technical hospital staff can operate without IT involvement.

The platform is feature-complete in mock mode. The core scaffold (117 files across Phases 0–9 of the build guide) is committed. Telemedicine sprints S6–S11 are complete. Wearables W1 + W4–W6 are on main; W2/W3 adapter wiring is running. Admin backend wiring (A1–A3) is in progress. The path to go-live is the L1–L9 launch gate — external credential injection, pen-test, content sign-off, and a controlled soft-launch (FRO pilot clinic first).

What's live on main today4,124 lines of new wearables code across 43 files (W1 + W4–W6). Full wearables API: consent engine, alert engine, FHIR Observation export, Garmin webhook, OAuth state, physician view, threshold UI, portal tab, consent management page, 8 test files, DPIA addendum, retention schedule, §L9 gate.

Soft-launch target: FRO pilot clinic

The FRO (Fyziatricko-rehabilitačné oddelenie / Physiatry & Rehabilitation) is the designated pilot clinic for online booking. All other clinics are read-only at launch. After a clean burn-in period (1–2 weeks), booking opens for all bookable=true clinics respecting their individual rules.

08

Architecture decisions log

All decisions below are locked. Do not re-open without strong justification — each has downstream consequences.

CMSKeep Strapi i18n plugin — not JSON {sk,en} per-field

A1 originally specified JSON bilingual fields. The shipped Strapi on main uses the native i18n plugin. With Ukrainian + Polish on the roadmap (6 locales total), i18n wins decisively — adding a locale is a Strapi config change, not a field migration. JSON {sk,en} would require migrating every field to {sk,en,pl,uk,cs,hu} and rewriting every API response.

AuthBrowser → Next proxy → NestJS (httpOnly cookie — JWT never in browser)

All portal API calls route through a Next.js proxy layer. The patient JWT is held in an httpOnly secure cookie and is never accessible to client-side JavaScript. This is the repo's established security pattern; wearables and telehealth both follow it.

AuthStaff JWT is separate from patient JWT

Different signing key (STAFF_JWT_SECRET), different aud claim (ns.staff). Staff tokens are never accepted on patient endpoints and vice versa.

Data modelNo physicians table — physician–patient via TelehealthSession

CLAUDE.md forbids a physicians table. Physician–patient relationships are resolved via TelehealthSession. Critical-alert SMS routes to a configurable escalation number (WEARABLES_ALERT_SMS_TO) until per-physician routing is available via A2 staff accounts.

HISNo direct web → HIS DB writes — all via RabbitMQ → sync agent → HL7/FHIR

Every HIS event is published to RabbitMQ and consumed by the sync agent, which translates to HL7 FHIR R4 (HL7 v2 fallback). The web tier never writes directly to the HIS database. Dead-letter queues capture failures for reconciliation.

FHIRReadings with fhir_observation_id are never deleted

Once a wearable reading has been exported as a FHIR Observation to HIS, it cannot be deleted — not even on consent withdrawal. The reading row is preserved; the patient_token reference is anonymised on GDPR erasure. Consent withdrawal soft-deletes readings without fhir_observation_id only.

LaunchSoft-launch: FRO pilot clinic only first

Online booking is enabled for FRO (Fyziatricko-rehabilitačné oddelenie) only at soft-launch. All other clinics are read-only. Full launch follows after a clean 1–2 week burn-in. A documented rollback (per-clinic kill switch + full traffic rollback) is mandatory.

PaymentsGP webpay primary, Stripe-EU backup — no PAN ever touches our servers

Payments use hosted fields / redirect. LSPP emergency fee €1.99. Webhook signature-verified. Payment receipts (PDF) generated server-side via Gotenberg/Puppeteer (EU only).

Non-negotiables

These constraints are enforced by config validators, DB triggers, and architecture. They cannot be bypassed in production.

Booking rules enforced server-sideA forged POST must be rejected. Client wizard UI is cosmetic. 10 negative-path integration tests prove enforcement at HTTP level.
MFA required for all staff accountsMFA_REQUIRED=true in production. Config validator enforces. No bypass. TOTP via authenticator app. Recovery codes generated at setup.
No patient RC (rodné číslo) in plaintextbcrypt hash for identity checks. AES-256-GCM encryption for NCZI XML generation. RC never logged, never in API responses.
audit_log append-only at DB layerREVOKE UPDATE/DELETE from app role + BEFORE UPDATE/DELETE trigger. No application-layer convention — the DB enforces it. Audit rows are never deleted; PII is anonymised on GDPR erasure only.
Machine-translated clinical content is always draftCS/PL/HU/UK locales require human review and approval before publish. Strapi lifecycle hook blocks publish if review_status !== 'approved'. No bypass.
EU hosting onlyDecree 179/2020. TLS 1.3. AES-256 at rest. No data transiting outside EU infrastructure. Huawei blocked until adequacy decision. GDPR export files never leave EU storage.
Telehealth recording disabled in productionTELEHEALTH_RECORDING_ENABLED=false. Requires TELEHEALTH_RECORDING_DPO_APPROVED=true to override. Physician join requires MFA re-verify at the endpoint — not just an active session.
OIDC_MOCK_ENABLED=false and HIS_MOCK_ENABLED=false in productionConfig validator enforces. WEARABLES_PROVIDER=mock is also rejected in production. CMS_AUTH_BYPASS=true rejected in production.
WCAG 2.1 AA — legal requirementAct 351/2022. axe-core must return zero critical/serious violations on every route before launch gate passes. Keyboard-only booking pass required. High-contrast + 130% text-resize must not break layout.

Language roadmap

The platform is built for six languages. Slovak is the human-authored source of truth. English is human-authored alongside it. Four additional locales are machine-translated with a mandatory human review gate before publish.

With Ukrainian and Polish confirmed on the roadmap, the Strapi i18n plugin (not JSON per-field bilingual) is the correct architecture — adding a locale is a Strapi config change, not a DB migration.

Translation review gate is a safety ruleClinical content (departments, clinics, services, news) in CS/PL/HU/UK is always a draft. A person must read and approve each translation before it goes live. An unreviewed page stays hidden in that language — which is safer than publishing a mistranslation. The Google Cloud Translation glossary preserves medical and department terms across all locales. Translation review UI is in Sprint A3.

Launch gate L1–L9

Nine sequential items between feature-complete and live. OPS items (L1, L4, L5, L6) are provisioning, backup, monitoring, and pen-test — run by operations. BUILD items (L2, L3, L7, L8) are paste-ready Claude Code prompts. L9 is the joint go/no-go gate and staged rollout.

Sequencing constraintL1 (secrets) must precede L2 (smoke tests) which must precede L3 (full CI suite). L4/L5/L6 run after L3. L7/L8 are human + build tasks that can run in parallel with L4–L6. L9 requires all 8 prior items green.

L9 — Go/no-go gate → soft-launch → full launch

When all 8 items above are green: hold a go/no-go review, cut DNS to production, enable FRO booking only, monitor for 1–2 weeks, then widen to all bookable=true clinics. Rollback trigger criteria and the L4 restore runbook must be on standby throughout launch week.

What remains is operational: content authoring by hospital staff, periodic accessibility + security re-audits, dependency/patch maintenance, monitoring queue/DLQ health, and rolling CS/PL/HU/UK out of draft as staff complete reviews.
